Ten Seconds of Primes

Optimizing Prime Sieving Across CPUs and GPUs

15-418 Project Proposal
Gabe Pacella

Project URL: https://gpack2.github.io/15418-final-project/

Summary

I will implement and optimize a segmented prime sieve to count as many primes as possible in ten seconds on the hardware available to me. The core project will compare an optimized multicore CPU implementation with an NVIDIA GPU implementation, with AMD GPUs and distributed execution as stretch goals.

Background

The Sieve of Eratosthenes finds primes by marking multiples of smaller primes as composite. A segmented sieve processes a limited interval at a time, allowing it to count primes over large ranges without storing all candidates simultaneously. To sieve through a chosen upper bound N, it first generates the base primes through the square root of N.

After generating the base primes, separate intervals can be processed independently. This provides parallelism across CPU cores, GPU thread blocks, and potentially separate computers. Each worker marks composites in its interval and counts the unmarked entries. I will store only odd candidates and handle 2 separately.

The goal is to maximize the number of primes counted in a completely checked interval beginning at 2. I will investigate how the implementation should change for each architecture, including memory representation, segment size, and work assignment.

The challenge

Memory locality. Marking multiples creates strided writes. CPU segments must balance cache locality against setup overhead, while GPU work assignment affects memory access efficiency.
Storage and synchronization. Bits reduce storage but require bit manipulation. Concurrent GPU writes to the same location, including different bits of one word, require ownership rules or appropriate synchronization to avoid races.
Load balance. Small primes require more marking operations than large primes. Work assignments must account for these differences while exposing enough parallelism.
Parallel overhead. Thread coordination, GPU launches, allocation, initialization, transfers, and counting can reduce time available for useful sieving.
Architecture differences. CPU and GPU versions may need different strategies. I will compare successive optimizations on the same hardware to distinguish software improvements from hardware differences.
I hope to identify the dominant bottlenecks on each architecture and explain how implementation choices affect them.

Goals and deliverables

Plan to achieve

  • A correct sequential segmented sieve and benchmark harness that count primes without printing or retaining the full list.
  • An optimized multicore CPU version, including comparisons of byte and bit storage for odd candidates, segment-size tuning, and thread-scaling measurements.
  • A correct NVIDIA GPU version, with experiments on work assignment, memory representation, and launch configuration.
  • Repeated ten-second runs and fixed-range tests reporting prime counts, completed upper bounds, runtime, throughput, and variation.

I aim to maximize the verified prime count achieved by my implementations in ten seconds. I will establish baselines before setting numerical speedup targets. Success will mean correct CPU and GPU versions, measured improvements from optimization, and an explanation of the remaining performance limits.

Benchmark rules

Each run will use a declared search ceiling and process segments beginning at 2. Its score will be the number of primes in the largest contiguous prefix whose counts have completed and reached the host before the ten-second deadline. Later segments separated by an unfinished interval will only count once the gap closes. Results arriving after the deadline will be excluded.

The primary timed interval will begin after program startup and device-context initialization, with no precomputed prime tables. It will include base-prime generation, working-buffer allocation and initialization, required transfers, sieving, and result counting. Costs outside this interval will be reported separately. Fixed-range benchmarks will use equivalent timing boundaries and wait for all required device work to complete.

Platform choice

CPUs provide a starting point for studying cache behavior, compact storage, and multicore scaling. NVIDIA GPUs provide a different execution model for the same workload and let me investigate parallel work assignment, memory access, and synchronization in CUDA.

This comparison aligns with my interest in accelerator software and performance engineering. The AMD GPU, laptop cluster, and possible PSC access provide additional experiments after the core implementations are complete.
